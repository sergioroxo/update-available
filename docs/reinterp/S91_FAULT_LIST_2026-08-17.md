**How this was played:** `?reinterp=1&debug=1`, cold boot, real pointer clicks in the
sandboxed Claude Browser pane. The pane suspends `requestAnimationFrame` for a hidden
document (previously-documented project quirk); frames were advanced by calling
`window.__app.tick(timestamp)` directly with a manually-incremented real timestamp
(NOT `app.tick()` with no argument — that reads a captured `performance.now` reference
and produced near-zero `dt`, which was caught and corrected before trusting any of the
below). Camera drag-to-look was driven with real `left_click_drag`, using the engine's
own documented sensitivity (`camYaw -= dx*0.16`, `src/engine/app.ts`) to compute exact
drag distances for target bearings, cross-checked against `window.__camPose()` after
every move. This is the same "hits off `__os.*.hits`, rAF stepper" technique this
project's own memory already names for this sandboxed pane.

Puppeteer (the project's usual real-Chrome path for persisted screenshots) was
attempted and **did not work in this environment**: `window.__app` never appears after
`Log in` under headless Chrome 151 + `--enable-unsafe-swiftshader`/`--use-angle=swiftshader`,
with no console error and no pageerror — module graph loads fully (98/98 requests
resolved, nothing pending), so the stall is inside PlayCanvas's own device/app creation,
not asset loading. Not diagnosed further under this session's budget. **Practical
consequence: no persisted on-disk screenshots from this session** — findings below were
confirmed by direct, live inspection in the interactive pane (camera pose, scene-graph
queries, hit tables, screenshots viewed inline), not by a file a person can open later.
This is a real gap against the brief's "save them where a person can look" instruction,
named honestly rather than papered over with an unverified screenshot path.

## 1 · ⚑ CONFIRMED FIXED — the duck is genuinely visible and reads as a duck

Camera placed at the exact authored Room-1 seat (`0, 1.16, 0.7`), turned to yaw **-84.32°**
(pitch ~0°) — the live-measured bearing to `rainbowDuck`'s world position
(`1.98, 1.67, 0.5`), not a guess. At that framing the top bookcase shelf shows a small
rounded yellow shape distinctly different in silhouette from the rectangular green
book (`book3`) 10cm away on the same shelf. **This is a real fix, not a fourth
coordinate confirmation** — S90's `rubberDuck.glb` (texture-stripped, scale 1.3) reads
as an object with a duck's silhouette, unlike the flat-colour placeholder box four prior
sessions confirmed was "correctly placed" and invisible-as-a-duck anyway. No action
needed here.

*Correction to my own first pass, recorded so the next session doesn't repeat it:* at
this same bearing I initially saw an enormous blown-out white/yellow glow filling the
whole frame and nearly wrote it up as a lighting bug (the lamp/window overexposing).
It was **my own test artifact**: an earlier diagnostic had called
`camEntity.setLocalEulerAngles(0, 84.16, 0)` directly on the CHILD `camera` node (the
one CLAUDE.md documents as gyro-only) instead of the drag-controlled rig, so my
injected rotation was silently *composing* with the rig's own rotation every frame —
confirmed by reading the entity's actual `getEulerAngles()` (roll ≠ 0, yaw ≠ what
`__camPose()` reported) against the debug pose function, which read the rig's state
and looked correct while the visible camera was wrong. Resetting the child's local
euler to `(0,0,0)` made the blowout vanish and the room render normally. **Not a
project bug — recorded as a "verify against running code" example, per this project's
own standing rule, of a plausible-looking false positive that a second check caught
before it became six.**

## 2 · ⚑⚑ NEW FINDING — `monkeyToy` and `tennisRacket` are not plainly visible from the Room-1 seat; the bed occludes them

Both are S90's new floor props, placed "off the foot of the bed" per their own
`_doc` in `data/room/reinterp_deltas.json` — `monkeyToyModel` at `(-1.2, 0, 2.4)`,
`tennisRacketModel` at `(-1.6, 0, 3.0)`.

Live-measured bearings from the seat: monkeyToy yaw **144.78°**, pitch **-27.86°**
(dist 2.35m); tennisRacket yaw **145.18°**, pitch **-22.14°** (dist 3.02m).
`camComp.worldToScreen()` at those exact poses puts both comfortably inside the
1280×720 frame (not clipped, not behind camera — `screen.z` positive for both).

**But turning the camera there and looking, at both the authored 42° FOV and a
tightened 12° FOV (to rule out "too small to notice"), the frame is dominated by the
bed's own near-field geometry** — `bedModel` sits at `(-1.53, 0, 1.15)`, only ~0.45m
past the seat along Z and squarely between the camera and both props along this
bearing. At 12° FOV aimed exactly at `monkeyToy`'s bearing, only a single dot of the
toy's own warm-brown colour is visible peeking through a gap between two bed-frame
rail segments — everything else in frame is bed frame. At `tennisRacket`'s bearing
(shallower pitch, same yaw-ish direction), the frame is entirely bed corner and open
floor; no racket-coloured shape is visible at all, on a real dark-grey
(`#44464F`) prop that should contrast against the warm floor if it were unoccluded.

This is the same class of failure the brief calls out for the duck/teddy
("correctly placed" is not the same as "visible") but with a different mechanism:
these two aren't uncontrasted boxes, they're occluded by the bed's own body from the
one seat the player actually sits in. **Verified against running code (entity
positions, real AABBs via `mesh getPositions`-derived `meshInstance.aabb`, real
`worldToScreen` projection, real screenshots at two FOVs) — not a comment, not a
manifest entry.**

**Proposed fix, not yet applied:** move both props to the open floor gap between the
bed's foot and the far wall corner (the space this session confirmed IS clearly
visible and unoccluded from the seat — a round rug sits there at
`(-1.48, 0, 1.72)`, `rugRectangle(Clone)`, and reads cleanly at this same camera
angle) rather than "beyond the foot," which sits directly behind the bed's own side
rail from the seat's specific vantage. This is a placement question, not a model or
scale problem — both meshes render correctly (checked: real materials, opacity 1,
enabled, non-degenerate AABBs) once unoccluded.

## 5 · Small, unconfirmed observation — not written up as a fault

At native pane resolution (800×450 screenshot of a 1280×720 viewport, 9px canvas
font), desktop icon labels ("Family Form" specifically) were briefly misread as
missing their leading letter. Checked against `drawIconInto`
(`src/desktop/os.ts:1841`): the label is centred, and `fitIconLabel` only trims
*trailing* characters before appending `...` — there is no code path that drops a
leading glyph. Almost certainly a resolution/anti-aliasing read on my part, not a
truncation bug. Recorded rather than silently dropped, per this project's "a comment
is not evidence" standard cutting both ways — I did not have persisted-file evidence
either way, so this is named as inconclusive rather than asserted as fixed.
